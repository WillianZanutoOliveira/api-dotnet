# Local development with .NET Aspire

## Recommended path

For daily development, run the AppHost:

```bash
dotnet run --project src/Platform/DistributedCommerce.AppHost
```

Aspire starts infrastructure, services and the dashboard.

Secret parameters are generated by the AppHost and stored in its local secret store.

## Prerequisites

- .NET 10 SDK;
- Docker or an Aspire-compatible Podman installation;
- a trusted ASP.NET Core development certificate for the best HTTPS Dashboard experience.

No legacy Aspire workload is required. The project uses `Aspire.AppHost.Sdk/13.6.0`.

The project keeps `AspireUseCliBundle=false` so the direct `dotnet run` workflow does not require a separately installed Aspire CLI. This is an intentional onboarding choice and should be revisited when the CLI bundle becomes mandatory in a future Aspire release.

## Main URLs

- Gateway: `http://localhost:8080`
- Orders: `http://localhost:8081`
- Inventory: `http://localhost:8082`
- Payments: `http://localhost:8083`
- Notifications: `http://localhost:8084`
- Keycloak: `http://localhost:8180`
- Vault: `http://localhost:8200`
- RabbitMQ Management: `http://localhost:15672`

The Aspire Dashboard URL is opened automatically by the AppHost launch profile.

## Dashboard security

The Dashboard is a development surface and can expose configuration, endpoints and sensitive telemetry. Keep it restricted to the developer machine/network. The AppHost keeps the Dashboard's default authentication mode; do not switch the frontend to `Unsecured` for a publicly exposed instance.

## Debugging

.NET services run as projects rather than published application containers.

This enables normal breakpoints in Orders, Inventory, Payments, Notifications and the API Gateway while infrastructure remains containerized.

## Vault remains mandatory

Aspire does not inject effective database passwords directly into services.

Orders example:

```text
Aspire-generated PostgreSQL admin password
          |
          v
orders-db
          |
          +------> vault-init configures Database Secrets Engine
                           |
                           v
                  Vault issues temporary login
                           |
                           v
                  Orders in-memory configuration
```

The application token lives at:

```text
.aspire/vault-tokens/orders/token
```

The directory is excluded from Git.

## Observability

Use the Aspire Dashboard for the development inner loop:

- stdout/stderr;
- resource endpoints;
- distributed traces;
- metrics;
- resource state.

Use secure Docker Compose when you want the full Grafana + Tempo + Prometheus demonstration.

## Docker Compose path

```bash
cp .env.example .env
docker compose -f docker-compose.yml -f docker-compose.vault.yml up --build
```

This remains the path closest to CI.

## Port conflicts

The AppHost intentionally uses stable local ports so Keycloak, Gateway and local scripts retain predictable URLs.

Stop older Docker containers or project processes when a port is already allocated.

## Local reset

Vault tokens are ephemeral. With the AppHost stopped, deleting `.aspire` resets AppHost-generated local token files. The directory is recreated automatically.

Clean Docker/Podman containers and volumes separately when required.

## Daily commands

Develop:

```bash
dotnet run --project src/Platform/DistributedCommerce.AppHost
```

Validate:

```bash
docker compose -f docker-compose.yml -f docker-compose.vault.yml config
dotnet build DistributedCommerce.slnx --configuration Release

```
